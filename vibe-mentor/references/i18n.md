# Internationalisation: French, English, Arabic (rule 8)

Read this before writing or reviewing any page or UI. The goal: the same screen works in three languages, and Arabic is a true mirror of the layout, not just translated text.

## 1. Structure

- **Locale files**, one per language, same keys: `locales/en.json`, `locales/fr.json`, `locales/ar.json`. Keys describe meaning (`signup.submit`), not the English text.
- **No visible string in components or templates.** Every label, button, placeholder, error message, `title`, `alt` and `aria-label` goes through the translation function. Server-side error messages shown to users are keys too.
- **A mature library** (rule 6): `i18next` (+ `react-i18next` / `vue-i18n` / the framework's own i18n module), or `Intl` for the platform parts. Do not write your own translator or placeholder engine.
- **Interpolation and plurals** through the library (`{{count}}`), never string concatenation: word order differs between the three languages.
- **Default language**: saved user choice → browser language (`navigator.language`, `Accept-Language`) → English. Show a visible language switcher on every page and remember the choice.

## 2. Formatting with `Intl`

Dates, times, numbers, currencies, relative times and lists use `Intl.DateTimeFormat`, `Intl.NumberFormat`, `Intl.RelativeTimeFormat`, `Intl.ListFormat` with the active locale. Arabic has **six plural categories** (zero, one, two, few, many, other): use `Intl.PluralRules` through the i18n library, and give all the forms that apply. Decide with the user whether Arabic shows Western digits (0-9) or Arabic-Indic digits (٠-٩); make it one setting, not scattered code.

## 3. Arabic: right-to-left mirroring

- On the root element: `<html lang="ar" dir="rtl">`. Switch `lang` and `dir` when the language changes, without a full reload if the app allows it.
- **CSS logical properties instead of physical ones**, so one stylesheet serves both directions:

  | Physical (avoid) | Logical (use) |
  |---|---|
  | `margin-left` / `margin-right` | `margin-inline-start` / `margin-inline-end` |
  | `padding-left` / `padding-right` | `padding-inline-start` / `padding-inline-end` |
  | `text-align: left` | `text-align: start` |
  | `left: 0` / `right: 0` | `inset-inline-start: 0` / `inset-inline-end: 0` |
  | `border-left` | `border-inline-start` |
  | `float: left` | `float: inline-start` |

- Flexbox and grid follow `dir` automatically: do not hard-code `row-reverse` for Arabic.
- **Mirror** what has a direction: navigation order, sidebars, breadcrumbs, back/forward arrows and chevrons, progress bars, sliders, "next" and "previous" icons, form label alignment, tab order.
- **Do not mirror**: logos and brand marks, photos, media playback controls, charts' time axes (usually), phone numbers, code samples, numbers and Latin words inside Arabic text (the browser's bidi algorithm handles them; wrap embedded fragments in `<bdi>` or `dir="auto"` when user text of unknown direction is inserted).
- Use a font that covers Arabic with a matching weight and a slightly larger line-height; never rely on a Latin-only font stack. Do not apply letter-spacing to Arabic text (it breaks letter joining) and avoid uppercase transforms.
- Icons that are only "decorative arrows" in an icon set: flip with `transform: scaleX(-1)` under `[dir="rtl"]`, or use the library's RTL variants.

## 4. Verification before delivering

1. Render each screen in `fr`, `en`, `ar`. For `ar`, check the layout is the mirror image, not merely right-aligned text.
2. Search the code for hard-coded user-facing text (grep for quoted words in templates/components) and for physical CSS properties (`margin-left`, `padding-right`, `text-align: left`, `left:`, `right:`).
3. Check long strings (French is ~20-30% longer than English) do not overflow buttons and menus.
4. Check forms: input direction (`dir="auto"` on free-text fields), validation messages, placeholders.
5. Say in one line what was internationalised, and flag the Arabic text for a native-speaker review when it is marketing, legal or medical copy.

## 5. Scope

Rule 8 covers pages and user interfaces. Command-line tools, scripts and logs may stay in English unless the user asks otherwise. Emails, PDFs and notifications generated for end users are user-facing too: use the same locale files and, for Arabic PDFs and emails, check right-to-left rendering.
